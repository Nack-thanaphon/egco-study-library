## คาบที่ 1 — Mathematical Modelling

### เรียนอะไร

- โมเดลคณิตศาสตร์คือภาพย่อของระบบจริง ไม่ใช่ระบบทั้งหมด
- ต้องกำหนด **system boundary** ว่ารวมอะไรและตัดอะไรออก
- ทุกโมเดลมี assumptions หรือสมมติฐาน
- หน่วยของค่าที่บวกหรือเปรียบเทียบกันต้องตรงกัน
- หลังแก้สมการต้องทำ validation และดู sensitivity กับ uncertainty

### อธิบายแบบง่าย

การสร้างโมเดลเหมือนทำแผนที่รถไฟฟ้า แผนที่ไม่วาดทุกตึกและต้นไม้ แต่เก็บเฉพาะสถานี เส้นทาง และจุดเปลี่ยนสาย เพราะนั่นคือข้อมูลที่ช่วยตอบคำถามเรื่องการเดินทาง

ขั้นตอนหลักมี 6 ข้อ:

1. ถามว่าต้องการรู้อะไร
2. กำหนดขอบเขตระบบ
3. เขียนสมมติฐาน
4. เขียนความสัมพันธ์เป็นสมการ
5. แก้สมการด้วยมือหรือคอมพิวเตอร์
6. ตรวจว่าผลใกล้เคียงความจริงหรือไม่

### คำที่ต้องรู้

- **Decision variable:** สิ่งที่โปรแกรมต้องเลือก
- **Parameter:** ค่าที่รู้และป้อนเข้าโมเดล
- **Objective:** เป้าหมายที่ต้องการให้ดีที่สุด
- **Constraint:** กฎที่คำตอบห้ามฝ่าฝืน
- **dx/dt:** อัตราที่ค่า x เปลี่ยนเมื่อเวลาเปลี่ยน

## คาบที่ 2 — Linear Programming Formulation

### โครงสร้างของ LP

```text
maximize cᵀx
subject to Ax ≤ b
           ℓ ≤ x ≤ u
```

อ่านเป็นเรื่องว่า “เลือกค่า `x` ให้ประโยชน์รวม `cᵀx` มากที่สุด แต่การใช้ทรัพยากรรวม `Ax` ต้องไม่เกินของที่มี `b` และตัวแปรต้องอยู่ในขอบเขตที่กำหนด”

โมเดล LP ที่ครบควรมี:

1. Sets หรือ indices
2. Parameters
3. Decision variables
4. Objective
5. Constraints และ bounds

### แปลคำจากโจทย์

- “ไม่เกิน” → `≤`
- “อย่างน้อย” → `≥`
- “เท่ากัน” หรือ “สมดุล” → `=`
- “ห้ามติดลบ” → `x ≥ 0`

### อะไรไม่เป็น Linear

LP ไม่ยอมให้ decision variable คูณกัน ยกกำลัง อยู่ในส่วนหาร หรืออยู่ในฟังก์ชันไม่เชิงเส้น เช่น `x₁x₂`, `x₁²`, `1/x₁` หรือ `log(x₁)`

### สถานะคำตอบ

- **Feasible:** ผ่านทุก constraint
- **Optimal:** ผ่านทุก constraint และให้ objective ดีที่สุด
- **Infeasible:** ไม่มีคำตอบใดผ่านข้อจำกัดทั้งหมด
- **Unbounded:** objective ดีขึ้นได้ไม่สิ้นสุด มักเกิดจากลืมข้อจำกัด
- **Slack:** ทรัพยากรที่ยังเหลือ ถ้า slack เป็นศูนย์แปลว่าใช้ถึงขีดจำกัด

## คาบที่ 3 — LP ใน Python และ Integer Programming

### ส่งอะไรเข้า `linprog`

- `c` คือสัมประสิทธิ์ของ objective
- `A_ub, b_ub` คือข้อจำกัดแบบ `≤`
- `A_eq, b_eq` คือข้อจำกัดแบบ `=`
- `bounds` คือค่าต่ำสุดและสูงสุดของตัวแปร

`scipy.optimize.linprog` แก้โจทย์แบบ minimize หากโจทย์เป็น maximize ต้องเปลี่ยนเครื่องหมายของ objective ก่อน แล้วเปลี่ยนกลับตอนอ่านผล

### อ่านผลอย่างไร

- `success` บอกว่า solver สำเร็จหรือไม่
- `x` คือค่าตัวแปรที่ได้
- `fun` คือค่า objective ในรูปที่ส่งเข้า solver
- `message` บอกเหตุผลเมื่อแก้ไม่ได้

อย่าหยุดที่คำว่า success ต้องแทนคำตอบกลับทุก constraint คำนวณ objective ซ้ำ และดู slack กับ utilization

### LP, ILP, Binary และ MILP

- **LP:** ตัวแปรเป็นทศนิยมได้ทั้งหมด
- **ILP:** ตัวแปรทุกตัวต้องเป็นจำนวนเต็ม
- **Binary:** ตัวแปรมีเพียง 0 หรือ 1
- **MILP:** มีทั้งตัวแปรต่อเนื่องและจำนวนเต็ม

จำนวน server 2.4 เครื่องใช้จริงไม่ได้ และการปัด 2.4 เป็น 2 หรือ 3 อาจทำให้ผิด constraint จึงต้องให้ solver รักษาเงื่อนไขจำนวนเต็มตั้งแต่ต้น

### Branch and Bound แบบภาพง่าย

1. คลายจำนวนเต็มให้เป็นทศนิยมชั่วคราว
2. ถ้าได้ค่าเศษ เช่น 3.6 ให้แยกเป็นกิ่ง `≤ 3` และ `≥ 4`
3. แก้แต่ละกิ่งใหม่
4. ตัดกิ่งที่ทำไม่ได้หรือแย่กว่าคำตอบที่มี
5. ทำต่อจนได้คำตอบจำนวนเต็มที่ดีที่สุด

## คาบที่ 4 — MILP สำหรับ Server และ ODE Introduction

### โมเดล Server

โจทย์ Server มักมีตัวแปรสองชุด:

- `qⱼ` = ปริมาณงานที่ส่งให้เครื่อง j แบ่งเป็นทศนิยมได้
- `yⱼ` = เปิดเครื่อง j หรือไม่ เป็น 0 หรือ 1

ข้อจำกัดสำคัญคือ `qⱼ ≤ capacityⱼ × yⱼ` ถ้า `yⱼ = 0` จะบังคับให้ `qⱼ = 0` จึงไม่มีงานไหลเข้าเครื่องที่ปิดอยู่ นี่เรียกว่า **linking constraint**

### งานแบ่งไม่ได้

ถ้างานหนึ่งต้องไปเครื่องเดียว ใช้ตัวแปร `xᵢⱼ` แบบ binary และเขียน `Σⱼxᵢⱼ = 1` สำหรับทุกงาน i จากนั้นตรวจ CPU, memory และสถานะเปิดเครื่องของแต่ละ server

### เริ่ม ODE

ระบบ static บอกความสัมพันธ์ ณ ขณะหนึ่ง ส่วนระบบ dynamic บอกว่าค่าจะเปลี่ยนตามเวลาอย่างไร

หัวใจของการสร้าง ODE คือ:

```text
อัตราสะสม = ไหลเข้า − ไหลออก + สร้างขึ้น − ถูกใช้
```

## คาบที่ 5 — ODE และ `solve_ivp`

### คำศัพท์ 5 ตัว

- **State x(t):** ค่าภายในระบบที่เปลี่ยนตามเวลาและต้องติดตาม
- **Input u(t):** สิ่งที่ป้อนหรือควบคุมจากภายนอก
- **Parameter θ:** คุณสมบัติคงที่ของระบบ
- **Output y(t):** ค่าที่ต้องการสังเกตหรือรายงาน
- **Initial condition x(0):** จุดเริ่มต้นของระบบ

### รูทีนตั้ง ODE

1. หา state ว่าโจทย์ติดตามอะไร
2. หา input ว่าป้อนหรือควบคุมอะไรได้
3. หา parameter ว่าอะไรเป็นคุณสมบัติคงที่
4. เขียน balance ว่าอะไรเข้า ออก เกิด และถูกใช้
5. จัดรูปเป็น `dx/dt = f(t, x, u, θ)`
6. ใส่ค่าเริ่มต้น
7. ตรวจหน่วย เครื่องหมาย และพฤติกรรม

### ตัวอย่างอุณหภูมิ CPU

```text
Cₜₕ × dT/dt = P(t) − (T − Tₐ)/Rₜₕ
```

เรื่องราวคือ “ความร้อนสะสม = ความร้อนที่สร้าง − ความร้อนที่ระบายออก” เมื่อกำลังไฟคงที่ จุดสมดุลเป็น `T* = Tₐ + P₀Rₜₕ` ดังนั้นห้องร้อนขึ้น ใช้ไฟมากขึ้น หรือระบายความร้อนได้ยากขึ้น จะทำให้อุณหภูมิสมดุลสูงขึ้น

ค่าคงตัวเวลา `τ = RₜₕCₜₕ` ช่วยบอกว่าระบบตอบสนองเร็วหรือช้า

### ใช้ `solve_ivp`

- `fun` คือฟังก์ชันด้านขวาของ ODE
- `t_span` คือเวลาเริ่มและเวลาจบ
- `y0` คือค่าเริ่มต้น
- `t_eval` คือจุดเวลาที่ต้องการดูคำตอบ
- `method="RK45"` คือวิธีเชิงตัวเลขมาตรฐานที่ใช้ในคาบ

ผลที่ได้เป็นค่าประมาณตามจุดเวลา จึงต้องดูกราฟ ตรวจหน่วย และถามว่าทิศทางสมเหตุสมผลหรือไม่

## คาบที่ 6 — Buffer Model, System of ODE และ SIR (20 ก.ย. 2569)

### Communication Buffer Model — จากสมการง่ายสู่ 3 เคส

จุดเริ่ม: buffer มีข้อมูลเข้า λ(t) (arrival rate) และออก μ(t) (transmit rate) โมเดลไร้เดียงสาคือ `dQ/dt = λ(t) − μ(t)` — สวยแต่ใช้จริงไม่ได้:

1. **Q=0 แล้ว μ > λ** → Q ติดลบ (เป็นไปไม่ได้ ของในคิวหมดแล้วส่งออกไม่ได้)
2. **Q=Q_max แล้ว λ > μ** → Q ทะลุความจุ (ของเข้าต้องถูกปฏิเสธ)

ทางแก้คือแยก 3 เคส:

| เคส | เงื่อนไข | สมการ |
|---|---|---|
| Empty | Q = 0 | `dQ/dt = max(0, λ(t) − μ(t))` |
| Normal | 0 < Q < Q_max | `dQ/dt = λ(t) − μ(t)` |
| Full | Q = Q_max | `dQ/dt = min(0, λ(t) − μ(t))` (ปฏิเสธของเข้า คิวคงที่) |

เหตุผลที่ไม่ฟอร์ส `dQ/dt=0` ตอน Q=0: ของเข้า-ออกพร้อมกันได้ (เข้า 10 ออก 5 ระหว่างที่ Q=0) เขียนเป็น λ(t), μ(t) ทั้งคู่จึง flexible กว่า

### Events ของ solve_ivp

```python
def empty_buffer_event(t, y):
    return y[0]            # ตัดแกน 0 = buffer ว่าง
empty_buffer_event.terminal = True   # พอเจอให้หยุด integrate
empty_buffer_event.direction = -1    # สนใจเฉพาะขาลง (+1=ขาขึ้น, 0=ทั้งคู่)
```

- event คือ list ของ callable — ใส่ได้หลายตัว (empty + full พร้อมกัน)
- **argument ของ event ต้องเท่ากับโมเดล** (t, y เหมือน fun)
- ผลอ่านจาก `sol.t_events[i]` และ `sol.y_events[i]` — ใส่กี่ event ก็มีกี่ชุด
- ส่วนใหญ่ set `terminal=True` เพื่อหยุด เช่น empty event ตั้ง direction=-1 (เปลี่ยนจากบวกเป็นศูนย์)

ตัวอย่างในคาบ: arrival 1, transmit 3 MB/s → Q หมดที่ t≈2.57 (empty event) | arrival 3, transmit 1, Q₀=20 → เต็มที่ t=5 (full event)

### System of ODE — CPU → Heatsink → อากาศ

ระบบสอง stage: Power เข้า CPU (C_P, T_P) → heatsink (C_H, T_H) → สิ่งแวดล้อม T_A โดย CPU ไม่แลกกับอากาศโดยตรง:

```text
Q_PH = (T_P − T_H)/R_PH      ความร้อน CPU→heatsink
Q_HA = (T_H − T_A)/R_HA      ความร้อน heatsink→อากาศ
C_P·dT_P/dt = P(t) − Q_PH
C_H·dT_H/dt = Q_PH − Q_HA
```

- จัดเป็น state-space ได้: `ẋ = Ax + Bu` เมื่อ x=[T_P, T_H], u=[P(t), T_A]; **A คูณ state, B คูณ input/parameter**
- โชคดี: solve_ivp ไม่บังคับจัด matrix — เขียนสมการตรง ๆ return `[dT_P, dT_H]` ก็ได้
- ตรวจด้วย conservation: สมการสองตัวบวกกัน → `C_P·Ṫ_P + C_H·Ṫ_H = P(t) − Q_HA` (ความร้อนรวม = เข้า − ออกทางเดียว)
- ค่าเริ่มต้น T_P=T_H=T_A → ไม่มีแลกเปลี่ยน (derivative ของ heatsink = 0); ฝั่ง CPU เหลือ dT_P/dt = P/C_P เช่น P=50, C_P=40 → 1.25 °C/s
- แนวคิด heat capacity C: ต้องใช้พลังงานเท่าไรจะอุณหภูมิ +1 — C ใหญ่ + P น้อย → แทบไม่ขยับ
- ถ้าให้ CPU แลกกับอากาศตรง ๆ ด้วย → เพิ่มพจน์ `−(T_P − T_A)/R_PA` (เข้าหนึ่งออกสอง)
- ทุกตัว (P, T_A, R, C) เปลี่ยนเป็น function of t ได้ เช่น P(t) = 50 ก่อน t=400, 75 หลังจากนั้น

### SIR Model — non-linear ตัวแรกของคาบเรียน

```text
dS/dt = −β·S·I/N
dI/dt =  β·S·I/N − γ·I
dR/dt =  γ·I
```

- S=Susceptible (ยังไม่ติด), I=Infected (ติดเชื้อ), R=Recovered (หายแล้วหายเลย)
- พจน์ βSI/N คือ **S×I คูณกัน** — นี่คือ non-linear ต่างจาก CPU–heatsink ที่คูณค่าคงที่บวกลบกันเฉย ๆ
- อัตราติดเชื้อขึ้นกับสองปัจจัยพร้อมกัน: คนยังไม่ติด S และคนติด I — ใครคนเดียวไม่พอ
- หน่วย: ทุกพจน์เป็นคน/เวลา; β, γ มีหน่วย 1/เวลา
- Assumption: ประชากรปิด N=1000 ไม่ย้ายเข้าออก; หายแล้วไม่กลับมาเป็น S (ถ้ากลับได้ต้องเพิ่มเส้น R→S)
- ตรวจ: dS+dI+dR = 0 → ประชากรคงที่ (แค่ย้ายสเตจ)
- ค่าที่ใช้ในคาบ: N=1000, β=0.3, γ=0.1, เริ่ม S=999, I=1, R=0 → จบ S≈60, R≈940, I→0
- ถ้า β สูงกว่า γ มาก → ติดเกือบหมดแล้วหายไป R เกือบ N; ถ้า γ ≥ β (หายเร็วกว่าติด) → การระบาดสะดุด เหลือคนไม่ติดเยอะ
- ตัวอย่างในโลกจริง: Plague Inc. สร้างบนโมเดลตระกูลนี้ (SIRD เพิ่ม Death)

## รูทีนแก้โจทย์ Optimization

1. ขีดเส้นใต้สิ่งที่ต้องเลือก
2. ตั้งชื่อตัวแปรและหน่วย
3. วงคำว่า สูงสุด ต่ำสุด ไม่เกิน อย่างน้อย และพอดี
4. เขียน objective กับ constraint
5. ระบุว่าตัวแปรเป็น continuous, integer หรือ binary
6. แก้ด้วย solver แล้วแทนค่ากลับทุก constraint
7. อธิบายคำตอบเป็นภาษาของโจทย์ ไม่รายงานแต่ตัวเลข

## รูทีนแก้โจทย์ ODE

1. เขียนว่า state คืออะไรและมีหน่วยอะไร
2. เขียน balance เป็นประโยคก่อน
3. เปลี่ยนประโยคเป็นสมการ
4. จัดอนุพันธ์ไว้ฝั่งซ้าย
5. ใส่ initial condition
6. ตรวจเครื่องหมายด้วยคำถามว่า “ถ้าไม่มี input ค่านี้ควรเพิ่มหรือลด”
7. ใช้ solver แล้วตรวจกราฟ จุดสมดุล และพฤติกรรมระยะยาว

## ตรวจความเข้าใจก่อนจบ

ผู้เรียนควรตอบได้ว่า:

- โมเดลต่างจากระบบจริงอย่างไร
- Parameter ต่างจาก decision variable อย่างไร

- Linking constraint ทำหน้าที่อะไร
- State, input และ parameter ในโมเดล CPU คืออะไร
- เครื่องหมายของอนุพันธ์บอกอะไร
- หลัง solver ให้คำตอบแล้วต้องตรวจอะไรบ้าง
